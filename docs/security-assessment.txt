SECURITY ASSESSMENT
UPDATED: 2026-11-08

CLASSIFICATION

Client-side tree-number consistency/invariant gap, with circuit-level
separation between nullifier binding and Merkle-root/path binding.

ESTABLISHED BY EXPERIMENTS

1. The native nullifier helper returned a hash for the tested
   out-of-range path index.
2. The tested Gnark circuits rejected the out-of-range index under
   BN254 Groth16 and PLONK.
3. Native Merkle proof generation preserved the originating tree
   number in the tested rollover scenario.
4. Four client proof methods reproduced a mismatch between the
   caller-supplied tree number and the Merkle proof tree number at
   the mocked proof-request boundary.
5. Initiator and destination handlers verified real Groth16 proofs.
   The tests demonstrated nullifier binding to the supplied tree
   number and independent Merkle path/root verification.
6. The inherited Solidity Merkle implementation rejected a root
   registered under one tree number when checked under the other
   tree number after a tested rollover. The runtime harness used
   mock Poseidon. See EXP-NF-010.
7. The inherited Solidity Merkle storage kept the same numeric
   nullifier independently scoped under tree 0 and tree 1.
   See EXP-NF-011.
8. The production EnygmaErc20CoinVault nullifyFromReceipt function
   recorded a nullifier under the tree number supplied in the
   receipt statement. The test used a placeholder nonzero root
   and zero proof coordinates. See EXP-NF-012.
9. EXP-NF-013 passed the same tree-1 proof through the real local
   client method and initiator handler with supplied stTreeNumber
   values of both 1 and 0. This establishes acceptance at that
   tested client-to-handler boundary.

10. EXP-NF-010B independently confirmed tree-specific root-history
    isolation after rollover using the generated production Poseidon
    libraries. The deployed wrapper's hash for [123, 456] matched
    circomlibjs exactly. Each tested root was accepted only under
    its originating tree number. This remains a Merkle harness test,
    not complete production vault proof validation.

ESTABLISHED BY SOURCE INSPECTION

1. The demo reconstructs Merkle trees from historical commitment
   events and separately supplies literal tree number zero to its
   initiator and destination proof methods.
2. The demo source therefore provides a path to a mismatched proof
   request after rollover.
3. Solidity source uses tree-specific root-history validation and
   tree-scoped nullifier checks.
4. The DvP first leg validates and stores a receipt and locks its
   input nullifiers.
5. The matching second leg retrieves and unlocks the pending receipt,
   revalidates both receipts, nullifies both inputs, and then inserts
   output commitments.
6. Asset-group membership checks a tree-zero root, but registered-vault
   membership is an alternative condition.
7. The ERC721 legacy ownership-proof tree-zero restriction is separate
   from its DvP destination verifier branch.

NOT ESTABLISHED

1. A deployed or production-environment 256-deposit rollover
   demonstration.
2. A post-rollover mismatched proof request against a deployed
   service. EXP-NF-013 is a local integration test.
3. Production vault rejection of a wrong-tree root through the
   complete receipt proof-validation path.
4. Successful settlement of a mismatched proof.
5. Successful exploitation, double-spending, or unauthorized
   asset movement.
6. Invalid on-chain settlement.

RECOMMENDED REVIEW

1. Enforce equality between the caller-supplied tree number and
   merkleProof.TreeNumber before constructing proof requests.
2. Add explicit native path-index validation for consistent
   API-level input handling.
3. Add production vault tests that exercise complete proof validation
   with a root registered under one tree number and submitted with
   another.
4. Add regression tests across client methods, circuits, proof
   handlers, and vault validation.
5. Test the complete DvP flow in an isolated local environment,
   including a post-rollover mismatched-tree scenario.
6. Keep note-tree validation distinct from asset-group membership
   validation in future security reviews.

FINAL CONCLUSION

The investigation demonstrates a reproducible client-side
tree-number consistency gap and a separation between circuit-level
nullifier verification and tree-specific Merkle-root validation.

The demo source provides a source-level path to a mismatched proof
request after rollover. EXP-NF-013 demonstrates that the same tree-1
proof can pass through the real local client method and initiator
handler with supplied stTreeNumber 1 or 0. Solidity source inspection
identifies downstream tree-specific validation and a DvP settlement
sequence that validates both receipts before nullifying inputs and
inserting outputs.

Solidity runtime tests now demonstrate tree-specific root-history
lookup in the inherited Merkle implementation with both mock and
generated production Poseidon libraries, tree-scoped nullifier
storage, and production vault receipt nullifier tree selection.
However, the production receipt test used a placeholder root and zero
proof coordinates. Complete production vault proof validation and
end-to-end settlement of a mismatched proof have not been demonstrated.

Exploitability, double-spending, and unauthorized asset movement
remain unestablished.

This is not a confirmed double-spend vulnerability.
