ENYGMA TREE-BOUND NULLIFIER INVESTIGATION
CONSOLIDATED TECHNICAL REPORT
Updated: 6 November 2026

1. RESEARCH QUESTION

Does Enygma consistently bind Poseidon-based nullifiers to the correct
Merkle tree and leaf index across native Go code, Gnark circuits, client
proof construction, proof handlers, and Solidity vault validation?

2. TARGET AND METHODOLOGY

Target repository: /workspaces/Enygma
Target branch: main
Target commit: a43586596644dd035ecd9e28ce6bc9022c1dec62

The investigation combined source-code inspection, native Go probes,
circuit tests using BN254 Groth16 and PLONK, mocked client proof-request
tests, handler tests using real Groth16 proof verification, and Solidity
source analysis.

The expected tree-bound nullifier index is:

globalIdx = treeNumber * 2^treeDepth + pathIndex
nullifier = Poseidon(secretKey, globalIdx)

Twelve experiments are recorded in evidence/experiment-register.txt.
Additional demo and Solidity settlement analysis is recorded separately
under source-analysis/.

3. NATIVE CODE AND CIRCUIT FINDINGS

3.1 Native nullifier helper

Source: enygma_dvp/src/core/utils.go
Function: GetNullifierWithTree

The helper calculates the global index from the supplied tree number,
tree capacity, and path index.

In the permanent depth-2 reproduction, path index 4 returned a nullifier
without an error, although valid indices are 0 through 3. The result
matched an independently calculated Poseidon hash using secret key
12345 and global index 4.

The permanent rerun specifically tests index 4. The earlier experiment
record also reports index 3 as an accepted control, but that control was
not independently rerun in the permanent reproduction.

Experiment: EXP-NF-002.

3.2 Circuit path-index enforcement

Source: enygma_dvp/gnark_circuits/primitives/Nullifier.go

The tested circuit rejected path index 4 at tree depth 2 under both
BN254 Groth16 and BN254 PLONK.

Experiment: EXP-NF-001.

3.3 Native Merkle tree rollover

Source: enygma_dvp/src/core/merkle.go

The permanent depth-2 reproduction inserted leaves 101, 102, 103,
and 104.

Under the default NewMerkleTree rollover condition, the fourth insertion
triggered rollover. The proof for archived leaf 103 identified tree 0
and returned its archived root. The proof for current leaf 104 identified
tree 1 and returned the current root.

The earlier EXP-NF-003 record separately describes leaf 101 as a tree-0
proof. The permanent reproduction uses leaf 103 and leaf 104.

Experiment: EXP-NF-003.

4. CLIENT-SIDE PROOF CONSTRUCTION

Four client methods were examined:

- DvPInitiatorProof
- DvPInitiatorProofFromSalts
- ZkDvpInitiateSwap
- DvPDestinationProof

In the tested scenarios, the Merkle proof identified tree 1 while the
caller supplied tree number 0. The client derived the nullifier using
the supplied tree number while constructing the request with the Merkle
proof root and path.

The mismatch was reproduced at the proof-request boundary using mocked
proof endpoints. These tests returned successfully, but the mock
endpoints supplied dummy proof data.

Experiments: EXP-NF-004, EXP-NF-005, EXP-NF-006, and EXP-NF-007.

Interpretation:
The examined client methods do not enforce equality between the
caller-supplied tree number and merkleProof.TreeNumber before constructing
the proof request.

Limitation:
These experiments do not establish successful cryptographic proof
generation, handler acceptance, on-chain execution, double-spending,
or unauthorized asset movement.

5. REAL GROTH16 HANDLER VERIFICATION

5.1 Initiator handler

Source:
enygma_dvp/gnark_circuits/server/circuits/dvpInit/handler_test.go

The test used real Groth16 proof verification.

Case A: Tree 1 with a tree-1 nullifier was accepted.
Case B: Tree 0 with a tree-1 nullifier was rejected.
Case C: Tree 0 with a tree-0 nullifier was accepted using the same
Merkle root and path.

Experiment: EXP-NF-008.

5.2 Destination handler

Source:
enygma_dvp/gnark_circuits/server/circuits/dvpDestination/handler_test.go

The same three cases produced the same acceptance and rejection
pattern under real Groth16 verification.

Experiment: EXP-NF-009.

Interpretation:
The tested circuits constrain nullifier derivation using the supplied
tree number and independently constrain the Merkle path against the
supplied root. The circuit does not independently establish that the
supplied root belongs to the supplied tree number.

Limitation:
These are handler-level cryptographic verification results. They do not
establish that a Solidity vault accepts a wrong-tree root or that an
invalid transaction can settle on-chain.

6. DEMO ROLLOVER REACHABILITY

Sources:
enygma_dvp/demo/main.go
enygma_dvp/src/core/merkle.go
enygma_dvp/contracts/core/contracts/vaults/Merkle.sol

The demo's loadVaultMerkleTree function queries historical
Commitment(uint256,uint256) events for a vault and replays the commitment
values into a native Merkle tree.

The demo uses Merkle depth 8, giving a nominal capacity of 256 leaves.

Both the default native tree insertion logic and Solidity insertLeaves
use a rollover condition that triggers when the next insertion makes
the current tree's leaf count reach the capacity.

For single-leaf insertions into a fresh tree, tree 0 holds 255 leaves.
The 256th insertion triggers rollover and is inserted into tree 1.
Other deposits or batch insertions can change the point at which this
boundary is reached.

The demo initiator step generates Alice's Merkle proof from the ERC20
vault tree and separately passes literal big.NewInt(0) as the tree
number to DvPInitiatorProof.

The destination step generates Bob's Merkle proof from the ERC721 vault
tree and separately passes literal big.NewInt(0) to DvPDestinationProof.

The examined client methods use the separately supplied tree number
for nullifier derivation while using the Merkle proof's root and path
for other proof-request fields.

This establishes a source-level path to a mismatched proof request
after rollover.

The demo reset endpoint resets in-memory workflow state; the inspected
implementation does not reset the blockchain or clear historical
commitment events. Repeated successful flows using the same chain and
vault addresses can therefore accumulate commitments.

Limitation:
No live 256-deposit demonstration or live post-rollover proof request
was performed. This is source-level reachability, not a runtime
demonstration.

7. SOLIDITY ROOT AND VAULT VALIDATION

7.1 Tree-specific root history

Source:
enygma_dvp/contracts/core/contracts/vaults/Merkle.sol

The root-history mapping is keyed by tree number and Merkle root.
The isValidRoot function checks the supplied root against the history
associated with the supplied tree number.

7.2 Vault receipt validation

The examined ERC20, Enygma ERC20, ERC1155, and ERC721 vault
implementations check roots and nullifiers using tree numbers supplied
in proof statements.

The ERC721 legacy ownership-proof branch explicitly rejects nonzero
tree numbers. Its DvP destination proof uses a separate verifier branch.
The legacy restriction must not be generalized to the DvP destination
branch.

7.3 DvP pending receipt and settlement

Source:
enygma_dvp/contracts/core/contracts/EnygmaDvp.sol
enygma_dvp/contracts/core/contracts/vaults/AbstractCoinVault.sol

The first leg of submitPartialSettlement validates the receipt and
checks asset-group membership before storing pending transaction
metadata and calling addPendingProofReceipt.

The vault stores the pending receipt and locks each input nullifier
using the tree number and nullifier contained in the statement.

When a matching second leg arrives, the DvP contract retrieves the
pending first-leg receipt using commitB and unlocks its input nullifiers.

The internal _settleOnGroupPair function checks message and commitment
relationships, counter-vault addresses, and asset-group membership.
It calls checkReceiptConditions for both receipts.

The settlement sequence nullifies inputs from both receipts before
inserting either receipt's output commitments.

The inspected settlement executes within an EVM transaction. A revert
reverts the preceding state changes in that transaction.

7.4 Asset-group membership

Source:
enygma_dvp/contracts/core/contracts/vaults/AssetGroup.sol

isMemberFromProofReceipt reads the final statement element as the
asset-group Merkle root and checks isValidRoot(0, assetGroupMerkleRoot).
The source includes a TODO to connect the tree number.

However, membership succeeds if either the vault is already registered
as a member or the asset-group root is valid in tree zero. A registered
vault can therefore satisfy the membership check without the asset-group
root check succeeding.

This is separate from the coin-vault note-tree root and nullifier checks.

7.5 Solidity runtime experiments

Three Hardhat runtime tests passed on 6 November 2026.

EXP-NF-010 tested the inherited Merkle implementation after a depth-2
rollover. A root registered under tree 0 was valid only under tree 0;
a root registered under tree 1 was valid only under tree 1. This
demonstrated tree-specific root-history lookup in the tested
implementation.

EXP-NF-011 tested the inherited Merkle nullifier storage. Numeric
nullifier 777 could be stored independently under tree 0 and tree 1.
The test did not exercise nullifier derivation or proof verification.

EXP-NF-012 deployed the production EnygmaErc20CoinVault and called
nullifyFromReceipt. The function recorded nullifier 777 under the
tree number supplied in the receipt statement. The test used a
nonzero placeholder root and zero proof coordinates. It did not
exercise complete receipt proof validation or DvP settlement.

The root-history and nullifier-storage tests used a local harness
with RuntimeMockPoseidon, implemented using keccak256 modulo the
BN254 scalar field. This is not production Poseidon.

These tests establish runtime behaviour for the tested Merkle
storage and receipt-processing paths. They do not establish complete
production vault rejection of a wrong-tree root through proof
validation or end-to-end settlement.

8. SECURITY ASSESSMENT

CLASSIFICATION:

Client-side tree-number consistency/invariant gap, with circuit-level
separation between nullifier binding and Merkle-root binding.

ESTABLISHED:

1. The native nullifier helper returned a hash for the tested out-of-range
   path index.
2. The tested Gnark circuits rejected that out-of-range index.
3. Native Merkle proof generation preserved the originating tree number
   in the tested rollover scenario.
4. Four client proof methods reproduced a mismatch between the
   caller-supplied tree number and the Merkle proof tree number.
5. Initiator and destination handlers verified real Groth16 proofs.
   The tests demonstrated nullifier binding to the supplied tree number
   and independent Merkle path/root verification.
6. The demo source separately supplies literal tree number zero to the
   examined initiator and destination methods.
7. Solidity source contains tree-specific root-history validation and
   tree-scoped nullifier checks.
8. The inspected DvP settlement path validates and locks the first
   receipt, then revalidates both receipts and nullifies both inputs
   before output insertion.
9. Asset-group membership has a tree-zero root check with a registered-
   vault alternative.

NOT ESTABLISHED:

1. A live 256-deposit rollover demonstration.
2. A live post-rollover mismatched proof request.
3. Runtime rejection or acceptance of a wrong-tree root by a deployed
   or locally executed Solidity vault.
4. Successful exploitation of the client-side mismatch.
5. Double-spending or unauthorized asset movement.
6. Invalid on-chain settlement.

9. RECOMMENDATIONS

1. Enforce equality between the caller-supplied tree number and
   merkleProof.TreeNumber before constructing proof requests.
2. Add explicit native path-index validation for consistent API-level
   input handling.
3. Extend Solidity runtime coverage to exercise complete production
   vault proof validation with a root registered under one tree number
   and submitted with another.
4. Add regression tests across client methods, circuits, proof handlers,
   and vault validation to preserve the same tree-number invariant.
5. Test the complete DvP flow in an isolated local environment,
   including a post-rollover mismatched-tree scenario.
6. Preserve the distinction between note-tree validation and asset-group
   membership validation in future reviews.

10. FINAL CONCLUSION

The investigation demonstrates a reproducible client-side tree-number
consistency gap and a separation between circuit-level nullifier
verification and tree-specific Merkle-root validation.

The demo source provides a path to a mismatched proof request after
rollover because it reconstructs Merkle proofs from historical
commitment events while separately supplying tree number zero.

The inspected Solidity source contains downstream tree-specific
root-history validation, tree-scoped nullifier checks, and a DvP
settlement sequence that validates both receipts before nullifying
inputs and inserting outputs. Asset-group membership also has a
separate tree-zero root check with a registered-vault alternative.

Runtime tests demonstrate tree-specific root-history lookup in the
inherited Merkle implementation, tree-scoped nullifier storage, and
production vault receipt nullifier tree selection. However, complete
production vault proof validation and end-to-end settlement of a
mismatched proof have not been demonstrated. Exploitability,
double-spending, and unauthorized asset movement remain unestablished.

This is not a confirmed double-spend vulnerability.
